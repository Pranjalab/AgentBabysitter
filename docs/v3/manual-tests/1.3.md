# Manual test — Step 1.3: first real absd run

This is the **first time absd touches your real bot.** The whole point of the
ordering below is to prove, in one sitting, that the daemon stays *silent* while
your interactive session owns the token, and only speaks once that session is
gone. Do the steps **in order** — the order is the test.

Everything runs as your user. No root except the one-time linger enable (Phase
1.8 will fold that into `install.sh`; for now you do it by hand).

Prerequisites: you already use ABS normally (a paired `default` profile with a
working bot), and the repo venv exists (`.venv/bin/python`).

---

## Phase A — install the unit (does NOT start anything)

1. From the repo root:

   ```
   abs daemon install
   ```

   Expected output: `✓ Installed user unit: ~/.config/systemd/user/absd.service`,
   a **linger** line, and a "Next steps" block. It must NOT say it started
   anything.

2. If linger is OFF (it will say so), enable it once so the daemon survives
   logout:

   ```
   sudo loginctl enable-linger $USER
   ```

   Re-run `abs daemon install` and confirm it now reports **Linger enabled**.

---

## Phase B — the silence test (daemon must NOT poll your live session)

This is the critical one. Your interactive `default` session is running and the
in-session telegram plugin owns the bot token. The daemon must see the live
`session.pid` and stay completely quiet.

3. Make sure you have a **normal ABS session live** in a terminal:

   ```
   abs
   ```

   Leave it running. (This writes `~/.abs/profiles/default/session.pid`.)

4. In another terminal, start the daemon:

   ```
   abs daemon start
   abs daemon status
   ```

   Expected: `status` shows the unit **active (running)**. Under it you may see
   `(no per-profile poller state yet)` — that's correct, because the poller is
   *yielding* to your live session and has not polled.

5. From your phone, send your bot a normal message, e.g. `hello from phone`.

   Expected: it behaves **exactly like today** — your live Claude Code session
   receives it via the plugin and replies. You get **no** "message saved to
   pool" ack, because the daemon is not polling. ✅ If you get a pool ack here,
   STOP — the daemon is wrongly polling a live session; capture
   `abs daemon logs` and do not proceed.

6. Confirm the daemon really is idle:

   ```
   abs daemon logs
   ```

   Expected: lines like `discovered 1 profile(s): ['default']` and the poller
   yielding — no `getUpdates`, no `sendMessage`.

---

## Phase C — the pool test (session gone → daemon answers)

7. End your interactive session from the phone (the kill-ladder rung) **or** the
   terminal:

   - Phone: send `ABS EXIT`, confirm when it asks, and it will run
     `abs --profile default exit`.
   - Or terminal: `abs exit`.

   This removes `session.pid`. Give it ~5 seconds.

8. From your phone, send a plain message, e.g. `pool me please`.

   Expected reply (verbatim):

   ```
   🗂 No session running — message saved to pool (1). Send ABS START to begin.
   ```

9. Send `ABS STATUS` (any case).

   Expected reply — a short status like:

   ```
   ABS STATUS — default
   Session: idle — no session running
   Pool: 1 message(s)
   Daemon: absd 2.6.0
   ```

10. Send `ABS POOL`.

    Expected: a numbered preview of what you pooled:

    ```
    🗂 Pool (1):
    1. pool me please
    ```

11. Send `ABS START`.

    Expected: it does **not** start a session yet (that lands in a later
    update). You get a distinct ack noting it isn't wired up and that your
    message was pooled.

12. **Stranger check (optional, if you have a second Telegram account):** from
    the account that is NOT on this bot's allowlist, message the bot. Expected:
    **total silence** — no reply of any kind. (Replying would leak that the bot
    is alive.)

---

## Phase D — back to normal, and shutdown

13. Start a normal session again and confirm the daemon steps back:

    ```
    abs
    ```

    Then from the phone send a message — your live session should handle it
    again (no pool ack), exactly as in Phase B.

14. Your pooled messages are still on disk (nothing is ever dropped). They'll be
    offered for forwarding once the ABS START flow lands (Step 1.5).

### Stopping / inspecting the daemon

- Stop it: `abs daemon stop`
- Status: `abs daemon status` (shows the unit + per-profile poller offset state)
- Logs: `abs daemon logs` (journal, or a tail of `~/.abs/daemon/daemon.log`)

### If something looks wrong

- Pool ack while a session is live (Phase B step 5) → daemon is polling a live
  session. Stop it (`abs daemon stop`), grab `abs daemon logs`, report.
- No pool ack after `abs exit` (Phase C step 8) → daemon not running or not
  seeing the profile. Check `abs daemon status` and `abs daemon logs`.
- To fully back out: `abs daemon stop`, `systemctl --user disable absd`,
  `rm ~/.config/systemd/user/absd.service`, `systemctl --user daemon-reload`.
