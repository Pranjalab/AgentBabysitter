# Manual test — blocked pings, pool multi-select, the daemon dot

Prereq: the daemon running (`abs daemon status` → active), a paired profile, a
phone with Telegram. **Section 1 needs herdr** — on tmux the feature is absent by
design, and section 1 should be skipped, not failed.

```sh
herdr --version                                  # present → section 1 applies
jq -r '.engine' ~/.abs/daemon/config.json        # "auto" or "herdr"
```

---

## 1. The session tells you it's stuck  (herdr only)

The one thing automated tests cannot cover: that herdr actually reports `blocked`
when a real claude waits for an approval.

1. From the phone, `ABS START` → pick a project → **Normal** (not Away — Away
   auto-approves, so nothing will ever block).
2. Give it a task that must ask permission, e.g.
   *"run `curl -s https://example.com | head -5` and tell me what it printed"*.
   The command must be one your Claude Code config does **not** auto-approve — if
   it runs without asking, pick something more intrusive (a write outside the
   project, an install).
3. Leave it alone. Within ~20–30s your phone should get:

   > ⏸ myrepo is waiting for input or approval (21s).
   > Answer here, or attach at the terminal: `abs attach default`

4. **Wait another two minutes without answering.** Expected: **no second ping**.
   One per block is the contract; a repeat is a bug.
5. Answer in the chat (the session owns the bot while live, so a reply reaches it).
   The task proceeds.
6. Trigger a second approval in the same session → you get pinged again (a new
   block is a new episode).

Check the trail:

```sh
grep session_blocked ~/.abs/daemon/events.jsonl | tail -3
# one line per block, with blocked_for_s — and NO message text
```

**Negative check (matters more than the positive one).** Do a session where you
answer every prompt within a few seconds at the terminal. Expected: **no pings at
all** — a block you already handled never needed one.

**Critique gate — false positives.** Use it normally for a day, then:

```sh
grep -c session_blocked ~/.abs/daemon/events.jsonl
```

Judge whether the count matches the number of times you were actually made to
wait. If it fires when nothing was blocked, `abs`'s side is fine — raise
`blocked_debounce_s` in `~/.abs/daemon/config.json` and restart the daemon.

**Turning it off:** set `"blocked_notify": false` (or raise the debounce) in
`~/.abs/daemon/config.json`, then `systemctl --user restart absd`.

## 2. Picking pooled messages by tapping

1. With **no session running**, send the bot three ordinary messages —
   e.g. `first`, `second`, `third`. Each is acked as pooled.
2. `ABS START` → pick a project → **Normal**. The pool screen appears with three
   ☐ rows and a `📤 Send all` / `🙈 Skip` row.
3. Tap row **1** and row **3**. Expected, each time:
   - the **same message updates in place** — no new screen per tap;
   - those rows become ☑, and the ticks also appear in the text above;
   - the action button becomes **📤 Send 2**.
4. Tap row **1** again → it unticks and the button returns to **📤 Send all**.
5. Tick 1 and 3 again, tap **📤 Send 2**. The session starts and its opening
   prompt contains `first` and `third` but **not** `second`.
6. `ABS EXIT`. Then `ABS POOL` → `second` is still there. Nothing you didn't send
   was consumed.

Also check the two shortcuts:
- Pool two messages, `ABS START`, tap **📤 Send all** without ticking → both arrive.
- Pool two, `ABS START`, tick one, then tap **🙈 Skip** → **nothing** is forwarded
  and `ABS POOL` still shows both. Skip overrules a tick.

**Nine or more pooled messages:** the toggles disappear and the screen says to
reply `send 1,3`. Confirm typing `send 2,4` still works.

## 3. The daemon dot on the status bar

1. In a session, look at the bottom bar: `abs:@yourbot · ● Text · ● Voice · ● Daemon`.
   With the daemon running, **Daemon is green**.
2. Stop it and open a new session:

   ```sh
   systemctl --user stop absd
   ```

   The dot goes **dim** (it may take up to 3 minutes — freshness is a 3-minute
   window on the status file's mtime).
3. `systemctl --user start absd` → green again within a poll cycle.
4. A machine with no daemon installed shows **no Daemon segment at all** — the
   v2 bar, unchanged.

## 4. Stale handoff sweep  (optional, destructive-ish)

Proves the daemon reclaims a marker whose session is gone. Do this with a session
you don't mind losing.

1. `ABS START` a session from the phone.
2. Kill it as brutally as possible, so the daemon never sees a clean end:

   ```sh
   pkill -9 -f 'claude --channel'
   ```

3. Normally the watch loop notices within seconds and you get "⏹ Session ended".
   That is the fast path and is the expected outcome — the sweep is the backstop
   for when even *that* is missed (a slept machine, an interrupted reclaim).
4. To exercise the backstop itself, confirm the marker is gone and the bot is
   listening again:

   ```sh
   ls ~/.abs/profiles/default/daemon-handoff.json   # should not exist
   abs daemon status                                # default: polling
   grep -E 'stale_handoff|session_end' ~/.abs/daemon/events.jsonl | tail -3
   ```

5. Send `ABS START` again — it must launch cleanly, with no "already running".
