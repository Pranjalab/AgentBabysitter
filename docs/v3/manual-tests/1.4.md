# Manual test — Step 1.4: multi-profile pollers (ADDENDUM to 1.3)

**Primary checklist is [`1.3.md`](1.3.md).** Do that one first — it proves the
core "silent while a session is live, answers once it's gone" behavior. This
addendum only covers what 1.4 *adds*, and honestly: with **one real bot today**
you can verify the per-profile status surface but NOT true multi-bot
concurrency. The multi-bot steps are marked ⏳ and wait for a second bot/profile.

Prerequisites: 1.3 done, daemon installable, repo venv present.

---

## What you CAN verify now (one bot)

### A — `abs daemon status` shows the per-profile line

1. Start a normal session and the daemon (as in 1.3 Phase B):

   ```
   abs            # in terminal 1 — writes session.pid
   abs daemon start   # in terminal 2
   abs daemon status
   ```

   Expected: the unit shows **active (running)**, and under **Profiles:** a line
   like:

   ```
   default: yielding-to-session (pid <n>)  pool=0  last-poll never ago
   ```

   The `yielding-to-session` state is the point — the daemon saw your live
   session and is standing down. `last-poll never` is correct (it hasn't polled).

2. End the session (`abs exit`, or `ABS EXIT` from the phone). Wait ~5s, send the
   bot a plain message from your phone (you should get the pool ack), then:

   ```
   abs daemon status
   ```

   Expected: the line flips to roughly:

   ```
   default: polling  pool=1  last-poll <a few>s ago
   ```

   `polling`, a non-zero `pool`, and a fresh `last-poll` age together prove the
   daemon is now the active consumer and the status file is being rewritten each
   cycle.

### B — boot-time / stale-pid sanity (optional, terminal only)

3. With NO session running and the daemon stopped, check the daemon notices a
   dead pid instead of being fooled by it. Simulate a stale pid file:

   ```
   echo 999999 > ~/.abs/profiles/default/session.pid   # a pid that isn't running
   abs daemon start
   abs daemon logs | grep -i stale
   ```

   Expected: a log line noting a **STALE session.pid** for `default`, and the
   daemon **polls anyway** (send a phone message → you get the pool ack). The
   `session.pid` file is left in place (the daemon does not delete it).

   Clean up: `abs daemon stop` and `rm ~/.abs/profiles/default/session.pid`
   (only if you created it here and no real session is running).

## What WAITS for a second bot ⏳

These need a second paired profile (a second bot token) — defer until you set one
up. They are the real G5 proof.

- ⏳ **Independent pooling.** Two idle bots; message each → each pools *separately*
  (`abs daemon status` shows two lines with independent `pool=` counts).
- ⏳ **Independence under fault.** One session live (that bot yielding) while the
  other bot keeps answering as the daemon — no cross-interference.
- ⏳ **Staggered start.** `abs daemon logs` at startup shows the pollers coming up
  a beat apart, not all at once.

The automated suite already proves all three against fake bots
(`tests/test_multiprofile.py`); this is the on-hardware confirmation for when the
second bot exists.

### If something looks wrong

- Status shows `polling` while a session is live → daemon is not yielding; stop
  it (`abs daemon stop`), grab `abs daemon logs`, report. (Same failure as 1.3
  Phase B.)
- No **Profiles:** block under `abs daemon status` → the venv/absd isn't
  resolving; the fallback prints raw status/offset files instead. Check
  `.venv/bin/python` exists.
