# Critique — Step 1.4: multi-profile pollers (G5)

## What was built

Step 1.3 shipped the loop-over-profiles *structure* (N staggered tasks) but only
proved single-profile behavior. Step 1.4 makes the multi-profile machine real,
correct, and proven under adversarial conditions.

- **Independent, supervised per-profile tasks** (`absd/__main__.py`
  `_run_profile`). Each profile is one asyncio task with its own
  `TelegramClient` (own token, own resolved `base_url`), own `Pool`, own offset
  file (`poller-<p>.json`), own status file (`status-<p>.json`), own backoff
  state, and its own `poller[<p>]` log prefix. A poller task that dies with an
  *unexpected* exception is logged **loudly** (`poller[<p>] DIED unexpectedly —
  restarting in Ns`, at ERROR) and **restarted** with exponential backoff
  (1s→2s→…→30s cap), in isolation — one profile restarting never touches another.
- **Narrowed the run-loop catch** (`absd/daemon.py` `Poller.run`). 409 →
  backoff; an operational `TelegramError` (network/HTTP, already retried once in
  the client) → warn + nap and stay alive; **any other exception now propagates**
  to the supervisor instead of being silently swallowed. This is what makes the
  supervision testable and real: a genuine bug restarts the task loudly rather
  than spinning invisibly.
- **Staggered start** (`_run_profile` + `_run_forever`). `cfg.poll_stagger_s * i`
  before the first cycle **only** (R10); subsequent polls are not staggered.
- **Boot-time state detection** (`_log_boot_state` + `Profile`). At start, each
  profile is classified and logged: LIVE session (pid alive → starts yielding),
  STALE `session.pid` (pid **dead** → treated as idle, logged, **pid file left
  intact** — deletion is the launcher's / 1.5's job), BLOCKED, OFF, or idle. New
  `Profile.session_pid_on_disk()` / `has_stale_session_pid()` distinguish a live
  session from a stale pid so the daemon is never fooled into permanent deafness.
- **Per-profile status files** (`Poller.write_status`, atomic replace, 0600,
  each cycle + at startup + in `--once`). Schema: `{profile, state, pool_count,
  session_pid, last_poll_at, updated_at}`. `state` ∈ {`polling`,
  `yielding-to-session`, `off`, `blocked`} via `Profile.state_label()`.
- **`abs daemon status`** now renders a per-profile block (state, pool depth,
  last-poll age) via `python -m absd --print-status` (pure read of the status
  files; no network, no daemon contact), with a raw-file fallback if the venv is
  unavailable. `render_daemon_status` / `read_status_files` / `_fmt_age` are pure
  and unit-tested.
- **Per-profile base_url test seam** (see below).
- **Hardened supervisor teardown** (`_cancel_and_wait`): a supervisor cancelled
  directly at shutdown tears down its child `run_task` before re-raising, so a
  poller's aiohttp session can never be orphaned/leaked.

## Per-profile base_url mechanism + real-deployment safety guard

The 1.3 seam (`ABS_TELEGRAM_BASE_URL`, env, global) can only point *every* client
at one server — useless for a test with three fake bots. Added the **least-magical**
extension: a per-profile file `<profile_dir>/.telegram-base-url` containing one
URL. Chosen over a mapping env var because it lives beside the profile it affects
and needs no parsing grammar.

**Safety guard** (`_resolve_base_url`): the override is honored **only when it
points at localhost** (`127.0.0.1` / `localhost` / `::1`, checked via
`urlparse().hostname`). Any non-localhost value is **refused** with a loud ERROR
log and the global default is used instead — a stray or hostile
`.telegram-base-url` (e.g. `https://api.telegram.org` or `http://evil.example`)
can never silently redirect a real deployment. Absent file → global default →
`https://api.telegram.org` in production. Proven by
`test_resolve_base_url_refuses_non_localhost` / `_accepts_localhost` /
`_absent_file_uses_global`.

## Supervision design (restart policy, backoff)

1. **Isolation boundary is the task**: each profile runs under its own
   `_run_profile`; an exception in one never enters another's stack.
2. **Recoverable vs fatal**: 409 and `TelegramError` are handled *inside*
   `run()` (backoff / nap) and never trip a restart; every *other* exception
   escapes to the supervisor, which logs at ERROR and restarts `run()`.
3. **Backoff**: restart delay 1s, doubling to a 30s cap; the poller object is
   reused so its in-memory offset survives the restart (no redelivery), and a
   `stop` during backoff aborts the restart cleanly.

## RACE REVIEW — boot-time detection vs terminal launches (the gate)

The daemon's IDLE_POLLING and a terminal `abs` launch both compete for one
`getUpdates` consumer slot per token. Enumerating the interleavings:

| # | Interleaving | Outcome | Covered by |
|---|--------------|---------|------------|
| 1a | Daemon boots; `abs.sh` **already wrote** `session.pid` | boot detection sees live pid → poller starts yielding; never polls | 4.1 boot detection (`_log_boot_state` + per-cycle `should_poll`) |
| 1b | Daemon boots; `session.pid` **not yet written** (abs mid-launch) | poller classified idle, but `should_poll()` is re-checked before *every* cycle and again before the (staggered) first `getUpdates`; by then `session.pid` exists (abs writes it before `exec`) → yields. If it polls in the sub-ms gap before the plugin registers, it pools/acks one batch then yields | 4.1 per-cycle yield + pool (D14) |
| 2 | Daemon up, profile idle, mid long-poll; user runs `abs` **between cycles** | abs writes `session.pid` + `exec claude` → plugin registers `getUpdates`. Two consumers briefly ⇒ Telegram 409s one of them. Next daemon cycle sees `session.pid` → yields; the transient 409 backs off | per-cycle yield + 409 backoff |
| 3a | Session dies **after** `should_poll()` passed (saw no live pid), **before** `getUpdates` | if the plugin still holds the slot → daemon gets 409 → backoff; if the token is truly free → daemon polls correctly (RECLAIM, 1.5) | 409 backoff |
| 3b | `session.pid` is **stale** (process dead) — the deafness trap | `live_session_pid()` uses `os.kill(pid,0)`; a dead pid is NOT live → the daemon polls, and logs the staleness, leaving the file intact | boot stale-pid detection (**closed here**) |
| 4 | Two daemons double-poll | out of scope: single systemd unit (D1) | D1 |

**Most dangerous interleaving.** Not a crash — a *silent* one: **#3b, a stale
`session.pid` mistaken for a live session.** If the daemon trusted the pid file's
mere existence, a crashed session would leave the bot permanently deaf — no
poll, no error, no 409, nothing to back off from. Every other race resolves
itself (409 backoff, or the pool catching a stray message); this one has no
self-correcting mechanism, which is exactly why it is the dangerous one. It is
**fully closed in 1.4**: liveness is an `os.kill` probe, not a file-exists check
(`test_boot_time_stale_pid_polls_live_pid_yields`).

**Residual (acceptable window).** In #1b/#2, a message that arrives in the
sub-second window while a terminal session is launching may be received and
**pooled** by the daemon rather than delivered live to the just-starting session.
It is never *lost* (D14 keeps it; 1.7 forwards the pool on session start) — only
briefly *delayed*. The single-commit HANDOFF (1.5) tightens this further; for 1.4
the guarantee is "pooled, not lost."

## Tests (9 new; 157 total, green)

`tests/test_multiprofile.py` — all against per-profile FakeTelegram instances +
temp ABS_HOME; every dummy "live session" process is a real child reaped in a
`finally` (no leaked processes):

- `test_mixed_states_only_idle_polls` — A live / B idle / C blocked: only B hits
  Telegram (A & C get zero `getUpdates`), only B pools + acks.
- `test_409_isolation_other_profile_unaffected` — B is always-409; C keeps
  polling and pools normally; B's task stays alive (409 ≠ crash).
- `test_poller_death_is_supervised_and_restarted` — an injected exception kills
  A's first cycle; A restarts and pools its message; B undisturbed; a loud
  ERROR "DIED unexpectedly" line is asserted.
- `test_staggered_start_spreads_first_polls` — 3 profiles, stagger 0.2s; first
  `getUpdates` arrival times are strictly ordered and spaced (monotonic
  timestamps, no long sleeps).
- `test_boot_time_stale_pid_polls_live_pid_yields` — stale pid → polls; live pid
  → yields; both pid files untouched; boot logs assert LIVE + STALE.
- `test_restart_resumes_offset_no_duplicate` — B pools 1 + commits offset; a
  fresh set of pollers on the same ABS_HOME resumes from the committed offset
  with no redelivery / no second ack; A still yielding, C still blocked.
- 3× `_resolve_base_url` guard tests (refuse non-localhost / accept localhost /
  absent-file default).

## What is NOT tested / known gaps (what breaks first in production)

- **`test_restart_resumes_offset_no_duplicate` models restart by rebuilding the
  pollers, not by cancelling a live `_run_forever`.** The invariant it proves —
  a fresh poller loads the committed offset from disk and the fake confirms it
  without redelivery — is the crux, but the full "SIGTERM a running daemon and
  bring it back up" path is exercised only via `--once` e2e (`test_daemon_main`)
  and the cancellation teardown in the task-based tests. A true kill -9 recovery
  test is Step 1.8's remit.
- **The launch-window residual (#1b/#2) is reasoned, not stress-tested.** No
  chaos test yet hammers "message arrives exactly as a session launches"; that is
  Step 2.3's chaos harness (500-iteration invariant checks). Here it is argued
  from the mechanisms, not measured.
- **Supervisor restart backoff never resets to 1s while the task keeps dying.**
  A poller that crashes, runs briefly, then crashes again keeps the escalated
  backoff (it only resets when `run()` returns cleanly, which for an infinite
  loop means only on stop). For a *persistently* crashing poller that is the
  right behavior (don't hot-loop restarts); for a poller that crashes once an
  hour it means a slightly slower-than-ideal recovery. Acceptable; noted.
- **`last_poll_at` has 1-second resolution** (`utc_now_iso` truncates to
  seconds). "last-poll age" in `abs daemon status` is therefore ±1s — fine for a
  human glance, not a metric.
- **Status file is written every cycle** (atomic replace). At the 50s production
  long-poll that is negligible; if `poll_timeout_s` were set to 0 in a real
  deployment (not the default) it would write hot. Local-only, 0600, so no
  correctness or secrecy concern — just I/O.
- **Per-profile `.telegram-base-url` is a real file in the profile dir.** It is
  test-only and localhost-guarded, but it *does* exist on disk during tests
  under a temp ABS_HOME; it must never be created under the real `~/.abs` (it is
  not, by any code path — only tests write it).

## Deviations from PLAN.md

- Added `--print-status` to `python -m absd` (a pure status-file reader) so the
  bash `abs daemon status` can render the per-profile block without embedding
  JSON parsing in bash or contacting the running daemon. Documented in
  `__main__.py`; no network, exits 0 on an empty home.
- Extended the 1.3 `ABS_TELEGRAM_BASE_URL` seam with the per-profile
  `.telegram-base-url` file (localhost-guarded). Necessary: a multi-fake test
  cannot point three clients at three servers with a single global env var.
- Narrowed `Poller.run`'s `except Exception` to `except TelegramError` (plus the
  existing `Conflict409` / `CancelledError`). This is a behavior change from 1.3
  (which swallowed *all* exceptions in the loop); it is required for supervision
  to see and restart on genuine bugs. No 1.3 test depended on the blanket
  swallow (verified); all 148 remain green.
