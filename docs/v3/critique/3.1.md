# Critique — Step 3.1: sandbox image + lifecycle CLI (Phase 3, pulled forward)

`abs sandbox` runs Claude Code inside a disposable Ubuntu container. `absd/sandbox.py`
(`SandboxManager` + `python -m absd.sandbox`), `docker/sandbox/Dockerfile`, and the
`abs sandbox build|create|list|start|stop|destroy` bash shims.

## Design change vs PLAN G7/3.1 (user-requested — noted here)

The plan (G7/3.1) said the project lives **inside** the container in a named volume
("nothing shared"). The user wants **work synced live to a local dir**, so the jail
boundary moves: each sandbox `<name>` gets a **dedicated host folder**
`<sandbox_root>/<name>` (default `~/Projects/sandboxes/<name>`, created 0700),
**bind-mounted** at `/home/dev/workspace`. That one folder is the ONLY host path the
container can see; the rest of the host stays invisible. So the boundary is now
"exactly one dedicated folder shared" instead of "nothing shared" — still a tight
jail, and it satisfies the live-sync requirement. `config.sandbox_root` sets the root.

## Security checklist (PLAN 5.6) — verified against `docker inspect`

| 5.6 requirement | How it's met | Verified |
|---|---|---|
| no `--privileged` | never in `create_argv` | `docker inspect .HostConfig.Privileged == false` |
| no docker-socket mount | never in argv (`/var/run/docker.sock` absent) | `.HostConfig.Binds` = exactly one entry |
| only the one host mount | a single `-v <workdir>:/home/dev/workspace` | `.HostConfig.Binds == ["<workdir>:/home/dev/workspace"]` |
| non-root inside | `--user dev`; image drops the default `ubuntu` uid-1000 user and makes `dev` = host uid | `.Config.User == "dev"` |
| only explicit port publishes | `-p H:C` only when `--ports` given; parser admits digits+colon only | argv shape test; `parse_ports` rejects metachars |
| copied creds are the only host secret inside | `docker cp ~/.claude` (COPY, D8), not a mount; copies diverge, host untouched | integration: modify inside → host copy unchanged |
| tradeoff documented to the user | `abs sandbox create` prints the credential-copy warning | manual test |

The name is validated with the SAME jail as the ABS START "New folder" flow
(`flow.validate_folder_name`): no separators, no `..`, `[A-Za-z0-9._-]{1,64}` — so a
user-supplied sandbox name can never escape `sandbox_root`. The ports parser's regex
(`^\d{1,5}:\d{1,5}$`) admits no shell metacharacter, and every docker call is an
explicit argv list (never `shell=True`), so neither a name nor a port spec can inject
an argument.

## The exact `docker create` argv (verbatim)

```
docker create --name absd-sbx-<name> --user dev --restart no \
  -w /home/dev/workspace -v <host_workdir>:/home/dev/workspace \
  [-p <H:C> …] absd-sandbox:v1
```

No command after the tag — the image's `CMD ["tail","-f","/dev/null"]` keeps the box
alive to be exec'd into (`docker exec -it absd-sbx-<name> …`; `exec_argv` builds it,
used by 3.2).

## Credential handling (D8)

`docker cp <src> absd-sbx-<name>:/home/dev/` places `<src>` at `/home/dev/.claude`
as a COPY. `docker cp` preserves the source uid numerically, and the image's `dev`
user is created at the **host uid** (`--build-arg UID=$(id -u)`), so the copy lands
owned by `dev`. Because it is a copy (not a mount), edits inside the sandbox never
touch the host `~/.claude` — proven in the integration test by mutating the file
inside and asserting the host source is byte-unchanged.

## Testing note (a deliberate safety choice)

The integration test copies a **fixture** credentials dir, NOT the real `~/.claude`.
The spec described copying the real `~/.claude` and asserting it stays unchanged; I
used a fake source instead because the standing rule is "no real profiles/credentials
in automated tests", and a fixture proves the exact same mechanism (copy-not-mount,
divergence, `dev` ownership) without ever reading real credentials into a throwaway
container. **Production `abs sandbox create` copies the real `~/.claude`** (that is
the feature). The real `~/.claude` is never read or written by the test.

## Honest gaps / what breaks first

- **The copied credentials are the whole `~/.claude`**, which includes the ABS
  telegram channel state (bot tokens) and plugins — not just the OAuth credential.
  That is D8/plan behavior and the tradeoff is printed, but it is real secret
  exposure inside the sandbox. **3.2 should recommend a dedicated bot per sandbox**;
  a future refinement could copy only `.credentials.json` + minimal config.
- **`--restart no`** means a sandbox does not survive a Docker daemon restart / reboot
  (it stays created but stopped, and `abs sandbox start` brings it back). Intentional
  for a disposable box; noted.
- **No resource limits** (cpu/memory/pids) are set — a runaway build inside could
  starve the host. A `--memory`/`--pids-limit` default is a reasonable Phase-3
  follow-up; out of scope for 3.1.
- **Credential ownership relies on host uid == `dev` uid.** With `--build-arg UID`
  defaulting to the builder's uid this holds for the common case; a sandbox created
  from an image built by a different-uid user would have mismatched ownership (the
  copy would be root-owned or wrong). The manager builds with `$(id -u)`, so this is
  only a risk if the image is shared across users.
- **`docker cp` of `~/.claude` can be large** (sessions, caches) and slow; no
  filtering. Fine for typical sizes; noted.
- **Sandboxes are not yet session targets** — `create/start/exec_argv` exist, but
  wiring a sandbox as an ABS START / engine target (a claude session inside) is
  **Step 3.2**. 3.1 is the image + lifecycle only.

## Deviations from PLAN.md

- The bind-mounted dedicated host folder (user-requested; the headline change above).
- Integration test uses a fixture creds dir, not real `~/.claude` (safety, above).
