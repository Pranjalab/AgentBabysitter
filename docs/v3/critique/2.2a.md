# Critique — Step 2.2a: resume-first ABS START + "/" menu (pulled forward), and
# the second-incident safety fixes

Two UX features from Step 2.2 were pulled forward after the 1.5 live demo, and a
**second live incident** (the daemon killed live claude sessions) forced four
safety fixes into the same package. This file covers both — the fixes are the
important part.

## What was built (UX)

- **Resume-first ABS START.** Every successful launch — the daemon's HANDOFF *and*
  a terminal `abs` — is recorded in `~/.abs/daemon/recents.json` (`absd/recents.py`:
  per-profile, capped at 5, most-recent-first, dedup by resolved path, 0600,
  corruption-tolerant). The flow's first screen (`absd/flow.py` +
  `Poller._begin_flow`) offers up to 3 "▶ Resume `<label>` (`<age>`)" buttons +
  "🆕 New session"; a Resume is **one tap** → straight to HANDOFF with the recorded
  mode and `--continue`. No recents → the Step 1.5 project picker unchanged.
  Terminal launches record via `python -m absd.recents add` from `abs.sh`
  (`_record_recent`, guarded so a v2-only install never breaks).
- **Telegram "/" menu.** `/abs_start`, `/abs_status`, `/abs_pool` are accepted as
  grammar aliases (`canonical_command`: case-insensitive, single-token, `@botname`
  stripped; the D9 grammar is otherwise unchanged — everything else still pools).
  The daemon registers the idle menu (`/abs_start /abs_status /abs_pool`) while
  polling and the session menu (`/abs_exit`, `/usage`) at HANDOFF, via
  `set_my_commands`, **debounced** (persisted last-kind per profile). Session-side
  `/abs_exit` (optional `@botname`) is wired into `abs.sh`'s control hook as the one
  session slash alias for `ABS EXIT` — the other kill-ladder phrases stay text-only.

## How `--continue` is threaded through the launcher

`flow.build_launcher_argv(script, profile, away, resume=True)` appends `--continue`
to `bash <abs.sh> --profile <p> --daemon-start [--away] --continue`. `abs.sh`'s arg
parser treats `--profile`/`--daemon-start`/`--away` as its own global flags and
forwards **everything else** to claude (the `-*) cmd_run "$@"` dispatch → `exec
claude … "$@"`). So `--continue` lands on the real claude, resuming the most recent
conversation in the launch cwd. No `--` separator needed (verified:
`test_daemon_start_paired_skips_prompts_and_launches` exercises passthrough; the
resume e2e asserts `--continue` reaches the engine argv). A cwd with no prior
conversation just starts fresh — claude's own `--continue` semantics, not ours.

## Menu-swap design (debounce)

`Poller._ensure_menu(kind)` only calls `set_my_commands` when `kind` differs from
the last-set kind, which is kept in memory **and** persisted to
`daemon/menu-<profile>.json` — so a daemon restart doesn't re-register, and the
loop never hammers the API. Transitions that call it: `run()` start (idle or
session per state), `_do_handoff` (→ session), `reclaim` completion (→ idle). Not
called per poll cycle. Tests: `test_run_registers_idle_menu`,
`test_menu_debounced_across_restart`, `test_handoff_sets_session_menu_reclaim_restores_idle`.

## The second incident — three compounding defects, four fixes

Forensics (journal + zombie-session): the user ran terminal `abs`/attach while a
daemon-launched herdr session was live. Three defects compounded into the daemon
**killing a live claude** (22-min session ended 16:27:27; a fresh one 13s after
launch):

1. `cmd_run` had **no live-session guard** → terminal launch overwrote `session.pid`.
2. A raw `herdr session attach` (copied from the confirmation) **resurrected** a
   stopped session and opened a second workspace `w2` with a bare `$HOME` shell;
   `HerdrEngine._pane_of` took the **first** pane → returned w2's idle shell → the
   daemon read `is_alive` False while claude ran in `w1:p1`.
3. Both signals false → `_session_dead` True → RECLAIM → `engine.kill` **killed the
   live claude**. (`kill` itself was fine; the zombie was attach-resurrection.)

**FIX A — `cmd_run` live-session guard** (`abs.sh`). Before writing `session.pid`,
`session_live_pid()` checks the existing `session.pid` (`kill -0`); a live pid →
`die` with "Profile 'X' already has a live session (pid N) — attach with:
`abs attach X`, or end it with: `abs exit`". Applies to normal **and**
`--daemon-start` (belt-and-suspenders). A stale/dead pid is replaced normally.
Tests: `test_terminal_launch_refuses_when_session_live`,
`test_terminal_launch_proceeds_past_stale_pid`.

**FIX B — precise pane-targeted liveness** (`absd/engines/*`, `SessionHandle`).
`create_session` now returns a `SessionHandle(pane_id, pid)` — herdr `"w1:p1"`,
tmux `None`+pane_pid. `is_alive(profile, pane_id=…)` targets **that recorded pane
only**; a recorded pane that no longer exists reads command-dead (process-info
fails), never a fall-back to another pane. The daemon records the handle at HANDOFF
and passes `pane_id` to every liveness check. *Protocol change justified:* the
"first pane" heuristic is unsafe the moment a session has >1 pane (herdr attach
does exactly that); the optional `pane_id` keeps `list_sessions`/legacy callers
(`pane_id=None`) working. tmux is unchanged in behavior (single-pane, session dies
on command exit, attach spawns no panes) — the param is accepted for parity.
Test: `test_herdr_liveness_targets_recorded_pane_not_first` (injects a real second
workspace, asserts `is_alive(pane_id="w1:p1")` stays True, then False only when the
recorded pane's command dies).

**FIX C — clobber-proof pid signal + foreign-takeover yield** (`absd/daemon.py`).
`_session_dead` uses the **recorded launcher pid** (`_launched_pid`, captured at
create or first-alive from `session.pid`) — NOT the shared `session.pid` file a
terminal launch can overwrite — plus the recorded pane. `_foreign_takeover`: if
`session.pid` on disk is a **different, live** pid, a foreign terminal session took
the bot → the daemon **yields** (logs once, stays SESSION_LIVE, never reclaims/kills)
until BOTH the foreign pid and our recorded pane are dead. Tests:
`test_foreign_takeover_yields_not_reclaims`,
`test_session_dead_uses_recorded_pane_not_disk_pid`.

**FIX D — non-resurrecting attach** (`absd/daemon.py`, `absd/engines/cli.py`). The
HANDOFF confirmation now prints only the **safe** `abs attach <profile>` wrapper
(no raw engine command). `abs attach` resolves the owning engine (bug-2 fix) and
**re-checks `is_alive` immediately before `execvp`**, so a stopped session is never
attached (herdr `session attach` can auto-start — the re-check is the guard).
Residual race documented below. Test: `test_full_callback_flow_handoff` asserts the
confirmation ends with `abs attach default` and contains no `session attach`.

## Honest gaps / residual risks (what breaks first)

- **Attach re-check is TOCTOU.** `abs attach` re-checks `is_alive` then `execvp`s;
  a session that dies in that ~ms window could still be attached (and herdr might
  auto-start it). The window is tiny and the confirmation no longer hands out the
  raw command, but the race is real — a fully non-resurrecting attach would need a
  herdr "attach-only-if-running" flag (not available in 0.7.5).
- **Recorded pane/pid are in-memory; a daemon restart mid-session loses them.**
  They're persisted in `daemon-handoff.json`, but the poller does not yet
  re-derive SESSION_LIVE + recorded pane from the marker on restart (that's Step
  1.8). After a restart the daemon falls back to the boot yield (session.pid) and,
  on death, reclaims without the recorded-pane precision — a narrower but non-zero
  reopening of the FIX B/C window across a restart. Noted for 1.8.
- **`_launched_pid` capture depends on `session.pid` being written.** For herdr the
  engine can't report the job pid until the command foregrounds, so the daemon
  captures it from `session.pid` at first-alive. If abs.sh failed to write
  `session.pid` (it always does before exec), clobber detection degrades to the
  disk-pid fallback. Acceptable; abs.sh writing it is load-bearing and tested.
- **Menu at handoff races the plugin.** `set_my_commands` is independent of
  `getUpdates`, so it's safe, but for a *terminal-launched* session the daemon's
  `session_state` stays IDLE (it only tracks its own handoffs), so a terminal
  session gets the **idle** "/" menu, not the session menu. Cosmetic; a Phase 2.2
  refinement could detect terminal sessions.
- **`--continue` resumes the most recent conversation in the cwd, which may not be
  the one the user expects** if they ran other claude sessions there. It's claude's
  own selection; ABS records only the path, not a conversation id.
- **Recents label uses the registry label or basename at record time**; renaming a
  registered project's label later doesn't rewrite old recents rows.
- **Resume cap re-check is at tap time**, but like the rest of the flow the
  `max_sessions` count is a snapshot (small TOCTOU with a concurrent start); one
  human operator makes this theoretical.

## Deviations from PLAN.md

- Step 2.2's inline-keyboard pool selection and statusline dot are **not** here —
  only resume-first + the "/" menu were pulled forward (PLAN.md Step 2.2 note).
- Engine protocol changed: `create_session -> SessionHandle` (was `None`),
  `is_alive` gains optional `pane_id`. Justified above (safety); backward-compatible
  for `pane_id=None` callers. `daemon-handoff.json` gains `pane_id` + `launcher_pid`.
- Two 1.5 tests updated for the new confirmation (safe attach only) and the
  self-heal messaging; no coverage lost.

## Addendum — terminal resume-first start menu

Brought the resume-first experience to the terminal: an interactive `abs` with
recents shows a picker before launching (▶ Resume ×3, 🆕 New in this folder, 📁
Another project…), mirroring the Telegram flow.

**What was built.** New Python CLI surfaces reused by bash (no logic duplicated):
`python -m absd.recents list --json` (entries + humanized `age` via the SAME
`flow.humanize_age`) and `python -m absd.registry targets --json` (registered
projects + workspace-root children via the SAME `flow.enumerate_project_options`,
newfolder sentinel filtered out — no folder creation at the terminal). `abs.sh`
gains `_start_menu` (+ `_start_menu_apply` / `_start_menu_project`), `--new` /
`--resume` global bypass flags, `abs config start-menu on|off`, and applies the
choice via `START_CWD` (cd before exec) + `--continue`. The FIX A live-session
guard was extracted to `_guard_no_live_session` and now runs BEFORE the menu (never
offer a choice that would die) and again before the `session.pid` write.

**How the menu reads input (TTY handling).** The choice is read from **stdin**
(`read -r`), and the menu is gated on `[ -t 0 ]` — it shows only for a real
interactive terminal. A piped/redirected stdin (`abs < /dev/null`, or any
subprocess) is not a TTY, so the menu is skipped and the launch is byte-for-byte
today's behavior. Reading from stdin (not `/dev/tty`) keeps it testable: a real
pty makes `[ -t 0 ]` true, so the interactive path is covered end-to-end by a
`pty.fork` test that writes `1\n` and asserts the launch `cd`'d to the recorded
path with `--continue`. The non-interactive paths (non-tty, `--new`, `--resume`,
no-recents) are covered by the real-`abs.sh` fixture harness (a cwd/argv-dumping
stub `claude`). Choice-shape validation (which option a number maps to) lives in
bash but is trivial integer arithmetic; the option *content* (recents, targets,
ages) is Python and unit-tested.

**Bypass flags implemented.** `--new` (skip menu, fresh in cwd), `--resume` (skip
menu, resume top recent — falls back to fresh if no recents), `--daemon-start`
(implies no menu — the daemon path is non-interactive), and `abs config start-menu
off` (persisted `.no_start_menu`, default on).

**Gaps / residual.**
- The interactive `read` loop and the "Another project" sub-picker are exercised
  by the one pty test (resume-top path); the sub-menu's project-pick branch and the
  vanished-folder fallback are covered only by reading the code + the Python
  `targets` tests, not a second pty script. Low risk (same integer-choice logic).
- A menu choice's recorded path could vanish between the pick and the `cd`; handled
  by the pre-`cd` `[ -d ]` check in `_start_menu_apply` (falls back to fresh-in-cwd)
  and a final `cd … || die` guard, but a TOCTOU sliver remains (rare, and it dies
  cleanly rather than launching in the wrong place).
- `--resume`/`--new` are consumed as global flags, so `abs --resume --model opus`
  works, but an unknown `--flavour` still falls through to claude as today — no new
  validation, consistent with existing passthrough behavior.
- The menu shells out to the venv Python twice (recents, and targets only if "📁"
  is chosen); on a cold FS that's ~tens of ms. Negligible interactively; noted.
