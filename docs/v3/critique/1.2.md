## What was built

- **`absd/engines/herdr.py`** — `HerdrEngine` implementing the `Engine` protocol,
  driven entirely through herdr's CLI + JSON socket (D3: arms-length, nothing
  copied). Session = named herdr session `abs-<profile>` (a per-instance
  `session_prefix` is the herdr analogue of TmuxEngine's isolated socket; tests
  use `abs-test-<random>-`). `create_session` spawns a **detached headless**
  `herdr server` (`start_new_session=True`), polls a bounded wait-for-ready
  helper, `workspace create --cwd --env … --no-focus`, parses the root pane id,
  and `pane run`s the command as one shell-quoted string. `is_alive`, `kill`
  (full teardown: pane close → session stop → session delete, idempotent),
  `attach_command`/`attach_argv` (per recipes), `list_sessions`. All herdr calls
  go through one `_run` helper (argv list, never `shell=True`, timeout,
  `HerdrError` on non-zero). Parsing is **module-level pure functions**
  (`parse_session_list`, `pane_id_from_create`, `first_pane`,
  `parse_process_info`, `command_running`, `launched_pid`) — unit-tested without
  herdr.
- **`absd/engines/base.py`** — promoted `EngineError` here (see Deviations) so
  both backends share one failure type; the `Engine` Protocol and `SessionInfo`
  are unchanged.
- **`absd/engines/__init__.py`** — `get_engine`: `"herdr"` → `HerdrEngine`;
  `"auto"` → `HerdrEngine` if `available()` else `TmuxEngine` (D4 fallback), dumb
  and single-line per branch.
- **`absd/engines/cli.py`** — engine-aware: `--engine {tmux,herdr,auto}` (default
  `$ABS_ENGINE` or `tmux`). Lets `abs sessions`/`abs attach` target herdr with no
  `abs.sh` change (the env var passes through the shim). Default stays tmux so
  Step 1.1 behaviour/tests are untouched.
- **`abs.sh`** — untouched (engine-agnostic shim, as expected).
- **Tests** — `test_engine_shared.py` (14 cross-engine), `test_engine_herdr.py`
  (16 herdr pure/parse + attach + protocol), `test_get_engine.py` (5 factory,
  `auto` monkeypatched both ways), `test_engine_tmux.py` slimmed to the 10
  tmux-only pure/attach tests (the lifecycle bodies moved to the shared file).

## Env-passing mechanism (found) + visibility tradeoff

`herdr workspace create --env KEY=VALUE` (repeatable) — herdr's per-pane env
injection, the analogue of tmux `new-session -e`. **Empirically verified:** the
values reach the process launched by a later `pane run` (confirmed by reading
`/proc/<pid>/environ` of fake-claude) and do **not** appear on the pane's command
line / `ps` / pane title. `test_env_reaches_command_process[herdr]` proves it end
to end: fake-claude's `$$` (written from `$FAKE_CLAUDE_PID_FILE`) equals the pid
the engine reports. Tradeoff (same as tmux `-e`): readable by any same-user
process via `/proc/<pid>/environ` — fine for the non-secret launcher vars ABS
passes, but **secrets must never go this way** (PLAN 5.5). The Step 0.2 spike had
only passed the pid-file path inside the command args; `--env` is the general
mechanism and is a recipes-doc addition (below).

## is_alive: what herdr actually does, and how it was normalized

**Empirical finding:** unlike tmux (no `remain-on-exit` → the session vanishes when
the command exits), **herdr keeps the pane and session alive after the launched
command exits** — the pane's interactive shell reclaims the foreground. After
killing fake-claude directly: `session list` still `running:true`, `pane list`
still shows `w1:p1`, `process-info` still returns a foreground process (the bare
`/bin/bash`). So session/pane existence is **not** a liveness signal.

**Normalization:** the reliable, launcher-agnostic signal is
`foreground_process_group_id != shell_pid`. While a command runs via `pane run` it
owns the pane's foreground (fg_pgid = the command's own pid = its `$$`); when it
exits, the shell reclaims the foreground and fg_pgid collapses to `shell_pid`.
`is_alive` = session `running:true` **and** fg_pgid ≠ shell_pid. Measured: the
command foregrounds ~0.7 s after `pane run` (the pane shell sources `.bashrc` —
conda init — first), and the signal flips back within ~0.02 s of the command
dying. This matches TmuxEngine's contract ("true iff the launched command is
running") without depending on the launcher writing `session.pid` — correct,
because `Engine.is_alive(profile)` receives only the profile and must be
engine-native (session.pid stays a separate daemon-level check, PLAN 4.1). This
deliberately refines the Step 0.2 recipe's "session.pid primary" suggestion (see
recipes-doc changes).

## Known gaps / what would break first in production

1. **`is_alive` startup window.** For ~0.7 s after `create_session`, the pane
   shell is still sourcing `.bashrc` and the command has not foregrounded, so
   `is_alive` reads false. Callers already poll (the daemon watches liveness on an
   interval; tests use `_wait_until`), so this is a non-issue in practice, but a
   caller that checks once immediately after create would see false. Documented.
2. **`fg_pgid != shell_pid` assumes the launched command holds the foreground.**
   True for the real launcher/claude (runs in the foreground). A launcher that
   *backgrounds itself* would read as not-alive. The real `abs.sh` launcher execs
   claude in the foreground, so this holds; flagged for whoever wires 1.5.
3. **`list_sessions` does N+2 herdr calls** (session list, then pane list +
   process-info per running session). Cheap for a handful of sessions; each call
   has the 15 s timeout guard. No retry/backoff — the daemon owns retry policy.
4. **Server-readiness is wall-clock** (R-fragility from 0.2). `_wait_for_ready`
   polls `session list` for `running:true` with a 15 s budget; a heavily loaded
   box could need longer. Encapsulated in one bounded helper (no scattered
   sleeps), so the budget is one constant to bump.
5. **herdr pre-1.0 churn (R3, D13).** Parsing keys (`root_pane.pane_id`,
   `foreground_process_group_id`, `shell_pid`, `running`) are pinned to 0.7.5,
   protocol 17. A point release renaming any of these breaks create/liveness. The
   pure parsers degrade to empty/None rather than crashing, but the behaviour
   would silently regress — the recipes doc is version-stamped and the shared
   suite is the canary on every bump.
6. **Pane id assumed `w1:p1` in teardown helpers** (`_herdr_teardown` closes
   `w1:p1`). ABS always creates exactly one workspace/pane, so this holds; the
   engine itself re-derives the pane id from `pane list` (robust), only the test
   teardown hard-codes it as belt-and-suspenders before `session stop` (which
   reaps children anyway).

## Deviations from PLAN.md / recipes

- **`EngineError` promoted to `base.py`.** Step 1.1 kept it engine-local and
  explicitly sanctioned promoting it "if HerdrEngine wants to share it in 1.2".
  Both engines now raise it (herdr via a `HerdrError(EngineError)` subclass), so
  the parameterized `pytest.raises(EngineError)` catches either backend. `tmux.py`
  re-exports it, so the historical `from absd.engines.tmux import EngineError`
  import path is unchanged. The `Engine` Protocol and `SessionInfo` in `base.py`
  are **untouched** — this is the only base.py change, one exception class, and it
  *is* part of the contract (`create_session` "raises on duplicate"). Justified
  judgment call, not a plan contradiction.
- **`cli.py` gained `--engine`/`$ABS_ENGINE`.** Small forward-looking addition so
  the herdr manual test's `abs sessions` step works without touching `abs.sh`.
  Default is `tmux`, so nothing from Step 1.1 changes. The daemon's `config.json`
  engine selection is still Step 1.3; this is only the CLI adapter honouring a
  choice now that a second engine exists.
- **`attach_argv` on `HerdrEngine`** — mirrors the tmux convenience (not in the
  protocol). Nothing herdr-specific was added to `base.py`.
