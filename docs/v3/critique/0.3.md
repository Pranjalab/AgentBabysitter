# Critique — Step 0.3: Fake-claude + fake-telegram test harness

## What was built

- `tests/harness/fake-claude` (bash, executable): mimics the Claude Code process
  shape. Writes its own PID to a configurable `--pid-file` (session.pid-compatible)
  in every mode, then behaves per mode:
  - `normal` — runs forever, interruptible; SIGTERM/SIGINT → cleanup + exit 0.
  - `not-logged-in` — auth-style stderr message, exit 1 quickly (`--auth-delay`
    default 0, must stay < 5 s to sit inside the PLAN.md 1.6 detection window).
  - `crash-after-<N>` (or `--mode crash-after --crash-after N`) — sleeps N s, exits 42.
  - Unknown trailing args (the claude-style argv the launcher passes) are ignored.
  - Config via flags or `FAKE_CLAUDE_*` env vars; flags win. shellcheck-clean.
- `tests/harness/fake_telegram.py` (aiohttp): `FakeTelegram` class implementing the
  five Bot API methods the daemon uses (PLAN.md 4.5) and nothing else (others 404):
  - `getUpdates` with real offset semantics (confirm-on-advance, redeliver-until-
    confirmed) and long-poll (parks until an update is queued or `timeout` elapses).
  - `sendMessage` / `editMessageText` / `answerCallbackQuery` / `setMyCommands` —
    captured into `sent_messages` / `edited_messages` / `answered_callbacks` /
    `commands` for assertions; `sendMessage` returns a real `message_id`.
  - Fault injection: `inject_409(times)`, `set_always_409()`, `set_delay(seconds)`.
  - Test-side queue helpers: `queue_message`, `queue_callback_query`, `queue_update`.
  - Bookkeeping for invariants: `getupdates_calls`, `confirmed_offset`, `delivered_ids`.
  - Binds 127.0.0.1 on an ephemeral port only. Also runnable standalone for manual
    poking (`python -m tests.harness.fake_telegram`).
- Tests FOR the harness (30 total across the suite; 20 are harness tests):
  - `tests/test_harness_fake_claude.py` (6): executable bit; normal stays alive +
    writes correct PID + clean SIGTERM exit + PID cleanup; not-logged-in exits 1 < 5 s
    with a login-mentioning stderr; crash-after-N non-zero after ~N s (flag and env
    forms); unknown-args tolerance.
  - `tests/test_harness_telegram.py` (14): queued updates returned in order; advancing
    offset confirms and prevents replay (delivered_ids has no dupes); no-advance
    replays; partial confirm keeps the rest; 409-once-then-recovers (queued update
    survives the 409); always-409; callback_query queue+consume + answerCallbackQuery
    capture; sendMessage/editMessageText/setMyCommands capture; unknown method 404;
    long-poll wakes promptly on a new update; long-poll times out empty; response delay.

## What is tested (the critique-gate checklist, PLAN.md 0.3)

- **Offsets:** confirm-on-advance, redeliver-until-confirmed, partial confirm, and the
  "nothing replayed once confirmed, nothing lost before it" invariant via
  `delivered_ids == [1,2,3,4]` after a proper advancing poll loop. ✅
- **409:** injectable once and persistently; proven to return HTTP 409 + Bot API error
  body, and proven not to lose the queued update. ✅
- **callback_query:** queueable and consumable; data/from/message round-trip. ✅
- **Allowlist cases:** the *fake* is allowlist-agnostic by design — it just carries
  `from.id` on every update so the daemon (Step 1.3) can enforce the allowlist. The
  harness proves `from_id` is faithfully delivered on messages and callback queries;
  the allowlist decision itself is daemon code and is tested in 1.3, not here. (Called
  out so the 1.3 reviewer knows where that assertion lives.)

## What is NOT tested / known gaps (what would break first in production)

- **No concurrency/chaos yet.** The fake's long-poll uses a single `asyncio.Event`;
  it is written for one poller per instance (the real invariant — one getUpdates
  consumer per token). Multiple simultaneous long-polls against one instance are not
  exercised and the event/clear handling could race under that (irrelevant to correct
  daemon behavior, but a mis-written test could hang). The chaos test (PLAN.md 2.3) is
  where real concurrency gets stressed.
- **Param parsing is permissive.** `_params` merges query + JSON body + form; it does
  not validate types the way real Telegram does, and silently ignores a malformed body.
  Good enough for a fake, but it will accept payloads the real API would reject — so a
  daemon bug that sends a malformed request could pass tests here and fail in
  production. First thing I'd tighten if the daemon's client started drifting.
- **No rate-limit / 429 simulation, no webhook surface, no getMe / message-splitting.**
  Only the five methods PLAN.md 4.5 names. Fine for scope; noted for completeness.
- **fake-claude timing is wall-clock.** `crash-after-1` and the not-logged-in `< 5 s`
  assertions use real sleeps, so the suite spends ~4 s here. Under a very loaded CI box
  the `< 5 s` / `< 4 s` upper bounds could theoretically flake; bounds are generous.
- **not-logged-in stderr text is arbitrary.** By design the daemon must key off exit
  code/timing, NOT this string (PLAN.md 1.6). The test asserts only that "login"
  appears, to avoid encouraging string-parsing in the daemon.

## Deviations from PLAN.md

- None material. PLAN.md 0.3 names "`fake-telegram`" without prescribing language; I
  built it as an importable aiohttp `FakeTelegram` class (aiohttp is the one allowed
  HTTP dep, PLAN.md 4.4) rather than a standalone process, because the daemon tests
  drive it in-loop. It is *also* runnable standalone, so the "server" framing still
  holds.

## Security notes

- Binds `127.0.0.1:0` only — never a routable interface. No real Telegram/Anthropic
  traffic anywhere in the suite (PLAN.md section 10). No tokens or secrets used: the
  fake's token is the literal string `"TEST"`; fake-claude touches no credentials.
