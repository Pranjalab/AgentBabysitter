# Critique — Steps 2.1, 2.2 (remainder), 2.3

Built 2026-08-10, in one pass, because the three are the last of Phase 2 and each
is small on its own. What follows is the honest version: what exists, what is
tested, what is **not**, and where I deviated from PLAN.md.

## What was built

**2.1 — blocked-session notifications (G8).**
`absd/agentstatus.py` (pure), `HerdrEngine.agent_status()`, and the daemon wiring
in `Poller._check_agent_status()`, called from the alive branch of `watch_once`.
A block sustained past `blocked_debounce_s` (default 20s) sends `BLOCKED_MSG` to
the chat that started the session and emits `session_blocked`. `done_notify` is
the opt-in counterpart, off by default.

**2.2 remainder — pool multi-select + statusline dot.**
`build_pool_keyboard(texts, selected)` grows a ☐/☑ row per message and a
context-sensitive action button; `parse_pool_choice` gained `send` and
`("toggle", i)`; `Poller._repaint_pool()` edits the screen in place. `cmd_statusline`
in `abs.sh` grew a `● Daemon` segment.

**2.3 — lifecycle completeness.**
`sweep_stale_handoff()` + `_marker_is_stale()`, config `stale_handoff_after_s` /
`stale_handoff_check_s`, event `stale_handoff`, and `tests/test_chaos_lifecycle.py`.

The rest of 2.3's list was already in the tree from earlier steps and was verified
rather than rebuilt: crash-vs-clean-exit distinction (`_session_end_reason` with
`failed_start` / `sandbox_channel_down` / `foreign_takeover_cleared` producing
distinct notices), `ABS START` on a live profile (`ALREADY_LIVE_MSG`, attach hint),
and the max-concurrent cap (`_at_session_cap` / `AT_CAP_MSG`).

## Deviation from the plan — say it plainly

PLAN.md 2.1 says "Daemon (or a small watcher task) **subscribes** to the herdr
session socket `pane.agent_status_changed`". What shipped **polls** `herdr pane
list` on the existing 3s SESSION_LIVE watch tick.

Reasoning: the debounce is ≥20s, so a sustained block is sampled six or more times
before it can fire — push buys no accuracy here, only latency nobody can perceive
against a 20s gate. Against that it costs a persistent socket client, a reconnect
path, a second long-lived asyncio task, and a window in which a dropped connection
silently stops the pings with nothing reporting it. `agent_status` is already on
every `pane list` row (verified live against herdr 0.7.5, protocol 17), so the poll
adds one subprocess call per tick and no new failure domain.

This is an implementation detail of a step, not one of the section-3 locked
decisions, so I made the call rather than stopping. It is reversible: the pure
watcher takes `(status, now)` and knows nothing about where the status came from.

## What is tested

- `tests/test_agentstatus.py` (34) — the decision logic, pure. Debounce boundary,
  once-per-episode, re-arming, `unknown` holding an episode open, probe failure as
  `unknown`, done transitions, reset-between-sessions, clamping.
- `tests/test_blocked_notify.py` (21) — the wiring. Probe targets the *recorded*
  pane; goes to the starting chat; silent on a backend with no `agent_status`
  (tmux); silent while the session is still starting; a raising probe never
  disturbs the watch loop; plus the whole 2.3 sweep matrix.
- `tests/test_pool_multiselect.py` (26) — keyboard shape, the 64-byte callback
  limit, the toggle round-trip through a real `Poller`, "Send all with nothing
  ticked" still meaning all, and Skip overruling a tick.
- `tests/test_chaos_lifecycle.py` (5 seeds × 100 ops; `ABS_CHAOS_ITERS=500` for the
  plan's length) — I1 pool never loses a consumed message, I2 offset never goes
  backwards, I3 no marker outlives a session-less poller, I4 always converges.

Full suite: **656 passing** (from 570), `bash -n abs.sh` clean.

Mutation-checked: a pool that drops one write in five, and a sweep that never
clears the marker. Both are caught by all five chaos seeds now — **neither was,
when the test was first written**, because I1 read the pool to decide what the pool
should contain (circular) and `_pool_ids` pointed at `pool.json` when the file is
`pool.jsonl` (so it always read an empty set). Both are fixed; I1 is derived from
the server side. Recording this because a green chaos test that proves nothing is
worse than no chaos test.

## What is NOT tested

- **`blocked` has never been observed end-to-end.** Step 0.2 could not trigger it
  either (`docs/v3/herdr-recipes.md` item 7): it needs a real claude in Normal mode
  facing a non-allowlisted approval prompt, and herdr's blocked detection is
  deliberately strict. Everything from `agent_status == "blocked"` onward is
  covered; that herdr *reports* `"blocked"` at the right moment is unverified by
  me and is the point of the manual checklist.
- **The false-positive rate**, which is 2.1's stated critique gate. It needs a day
  of real use; `abs daemon logs` + `grep session_blocked ~/.abs/daemon/events.jsonl`
  is the measurement.
- **The statusline dot on macOS.** `find -mmin` exists on BSD find, but I verified
  the three branches (fresh / stale / no daemon dir) on Linux only.
- **The pool keyboard on a real phone.** Button-label truncation is tested as a
  string; how eight rows of toggles actually feel in Telegram is Pranjal's call.

## Known gaps carried forward

- A block that starts and ends entirely between two 3s ticks is never seen. That
  is correct — it also never needed a ping — but it means the feature samples
  rather than observes, and a pathologically flappy agent could stay under it.
- `_repaint_pool` falls back to sending a new screen when an edit fails; a burst of
  taps against a broken edit path would stack screens. Bounded by the user's
  patience, not by code.
- The sweep uses the marker's wall-clock timestamp, so a large clock jump
  backwards delays it. It cannot cause a wrong sweep — only a late one.
