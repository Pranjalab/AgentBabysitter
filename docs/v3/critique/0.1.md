# Critique — Step 0.1: Scaffolding

## What was built

- `absd/` Python package skeleton (stdlib-first, PLAN.md 4.4):
  - `__init__.py` — package doc + `__version__` (mirrors `ABS_VERSION` 2.6.0).
  - `__main__.py` — `python -m absd` entry **stub**; prints `absd: not implemented
    yet — see PLAN.md` to stderr and exits 1. No polling, no I/O.
  - `config.py` — `DaemonConfig` dataclass (the `~/.abs/daemon/config.json` shape
    from PLAN.md 4.3) with real `to_dict`/`from_dict` JSON round-trip; `load()` is a
    stub raising `NotImplementedError` (Step 1.3).
  - `telegram.py` — `TelegramClient` **stub**: the exact Bot API surface the daemon
    needs (get_updates, send_message, edit_message_text, answer_callback_query,
    set_my_commands), all raising `NotImplementedError`.
  - `pool.py` — `PooledMessage` (on-disk `pool.jsonl` record shape) + `Pool` **stub**
    (append/read_all/mark_forwarded/clear), all raising `NotImplementedError`.
  - `engines/base.py` — the `Engine` protocol **verbatim from PLAN.md 4.2**
    (`@runtime_checkable`) + `SessionInfo` dataclass. No engine implementations
    (TmuxEngine/HerdrEngine are Steps 1.1/1.2).
  - `engines/__init__.py` — re-exports `Engine`, `SessionInfo`.
- `pyproject.toml` extended: `[dependency-groups].dev` (pytest, pytest-asyncio,
  aiohttp), `[tool.pytest.ini_options]` (testpaths, `asyncio_mode = "auto"`, `-ra`).
  absd deliberately NOT added to the wheel build yet (see Deviations).
- `tests/`: `test_config.py` (6 tests: version sanity, defaults, round-trips, forward
  tolerance) + `test_skeleton.py` (4 tests: protocol runtime-check, SessionInfo,
  `__main__` stub returns 1, stubs raise NotImplementedError). 10 tests, all green.
- `docs/v3/` tree: `critique/`, `manual-tests/`, `herdr-recipes.md` placeholder.
- `abs.sh`: `cmd_daemon` stub (prints message, exits 1) wired into the early dispatch
  block (before jq/profile resolution) and into `cmd_help`. Minimal diff, house style
  (rationale comment, `info()` helper).

## What is tested

- pytest toolchain runs in the repo `.venv` (Python 3.13.9).
- `DaemonConfig` JSON round-trip (default + fully-custom + partial + unknown-key
  tolerance) — the on-disk config contract (PLAN.md 4.4) is locked by tests.
- `Engine` protocol is structurally satisfiable (`isinstance` via runtime_checkable).
- `python -m absd` and `abs daemon` both emit the not-implemented notice and exit 1
  (verified manually; the Python path also unit-tested via `main([]) == 1`).
- Stubs raise `NotImplementedError` (the Step 0.1 contract, not a bug).

## What is NOT tested (by design — later steps)

- No daemon behavior: no poller, no state machine, no allowlist, no pool I/O, no
  Telegram traffic, no engine. Every module with real behavior is a stub.
- `config.load()` disk semantics (0600, defaults-on-missing, validation) — Step 1.3.
- The `abs daemon` bash stub is exercised manually, not by an automated bash test
  (the repo has no bash test harness; adding one is out of scope for 0.1).

## Known gaps / risks (what would break first in production)

- **Nothing ships yet.** absd has zero runnable behavior; the only production-visible
  surface is the two stubs that refuse to run. That is intentional and safe (no
  half-built daemon can touch a real bot token).
- **First real risk when 1.3 lands:** `config.load()` and the Telegram client are the
  first code to touch disk and network. The stubs fix the *shape* but the round-trip
  test does not validate ranges (e.g. a hostile `poll_timeout_s: -1` would deserialize
  fine today) — validation is explicitly deferred to the loader. Flagged so 1.3
  doesn't assume the type layer guards values.

## Deviations from PLAN.md (with justification)

1. **absd is NOT added to the hatch wheel `packages`.** PLAN.md 4.3 lists `absd/` as a
   repo package but installer/packaging wiring is a Step 1.8 item, and absd has no
   runnable behavior. Shipping it in the wheel now would distribute a dead import.
   Documented inline in `pyproject.toml`; revisit at 1.8. (Judgment call, not a
   contradiction of the plan.)
2. **`config.py` contains real (de)serialization logic**, whereas the work-package
   brief called config a "stub … no logic." Justification: PLAN.md's own Step 0.1
   example test is a "config dataclass round-trip", which requires real `to_dict`/
   `from_dict`. I treated the *dataclass + JSON contract* as a stable spec artifact
   (PLAN.md 4.4) and kept only the *disk loader* as a stub. Net: minimal, pure,
   fully-tested logic; no daemon behavior.
3. Test deps installed into the **existing** `.venv` (the voice-pipeline venv, Python
   3.13.9 ≥ 3.11) per the brief's "use existing .venv if ≥3.11". Additive only
   (pytest/pytest-asyncio/aiohttp); does not disturb the voice packages. `.venv/` is
   gitignored, so this is not in the commit.

## Tooling note (honesty over polish)

- `shellcheck` is **not installed** on this machine. I fetched the upstream v0.10.0
  static binary into the session scratchpad (not the repo) to verify. Plain
  `shellcheck abs.sh` reports **22 info/warning findings — ALL pre-existing** (SC2155,
  SC2015, SC2016, SC2086 in code I did not touch). My changes add **zero** new findings
  (verified by diffing shellcheck output of HEAD vs working tree: identical 22).
  So "shellcheck stays clean" holds in the sense of *no new findings*; the repo's
  baseline is not zero-findings and never was. Not fixing the pre-existing baseline —
  out of scope and would bloat the diff.

## Critique-gate question (PLAN.md 6/0.1): does the skeleton match 4.3?

Yes for the repo-side layout: `absd/` (daemon, engines, telegram, pool, config),
`tests/`, `docs/v3/`. The `~/.abs/` runtime layout (daemon/config.json, registry.json,
pool.jsonl, daemon-handoff.json) is only *represented as types* here (DaemonConfig,
PooledMessage); the actual directory creation is Step 1.3+. `assets/abs.tmux.conf` is
NOT created (it's a Step 1.1 deliverable, tied to TmuxEngine).
