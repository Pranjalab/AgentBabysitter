# Critique — Step 3.2: sandbox as a session target

A sandbox is now a real ABS session target: `ABS START` (Telegram) or `abs start
sandbox` (terminal) runs Claude Code INSIDE the container, driven through the whole
stack — handoff, liveness, reclaim, attach — with the daemon's precision adapted to
the container boundary.

## Where claude runs (the architecture)

The engine (tmux/herdr) pane command becomes:

```
docker exec -it absd-sbx-<name> absd-session <profile> [--permission-mode acceptEdits] [--continue] [<initial prompt>]
```

`absd-session` (baked into the image at `/usr/local/bin/absd-session`) runs INSIDE
the box: it `cd /home/dev/workspace`, sets `TELEGRAM_STATE_DIR` to the copied
Telegram state, and `exec claude --channels plugin:telegram… "$@"`. The
**docker-exec CLIENT runs on the HOST** (in the pane) — that host process is what
the engine's liveness sees. The plugin's MCP server (bun) polls from inside the
box, so the bot is owned from within the container while the session is live.

## Liveness across the docker boundary (the key adaptation)

A sandbox session's `session.pid` (if the launcher wrote one) would be a
**container-namespace PID** the host daemon cannot `kill -0`. So for sandbox
sessions the daemon uses the **ENGINE PANE signal ONLY**:

- `_session_dead()` for a sandbox = `not engine_pane_alive()` — the host-side
  `docker exec` client. When claude exits inside the box, the exec client exits and
  the pane command ends → `is_alive` False → reclaim. **No host `session.pid` is
  consulted.** (Measured: the pane signal is reliable end-to-end in the real-docker
  test — `sandbox.process_alive(name, pattern)` exists as a documented `pgrep -f`
  fallback but is NOT needed/used.)
- `_foreign_takeover()` is **always False** for a sandbox: there is no host
  `session.pid` to clobber, and a terminal `abs` cannot take over a container
  session's bot the same way — so the FIX-C clobber check is meaningless across the
  boundary and is skipped.
- `watch_once` skips the host-`session.pid` pid-capture for sandbox sessions.
- **Recovery**: the marker records `"sandbox": "<name>"`; on restart a sandbox
  session recovers via the pane only (the marker's `launcher_pid` is NOT treated as
  a host-alive signal). Live pane → resume SESSION_LIVE; dead → reclaim.

**The marker field is `sandbox`** (in `daemon-handoff.json`), set BEFORE launch so
watch/recovery see it immediately.

## The container survives session end (confirmed)

Reclaim kills the ENGINE session (the docker-exec pane) via `_kill_engine_session`
— it does NOT touch the container. `abs sandbox stop|destroy` is the separate,
explicit lifecycle. The test `test_sandbox_session_end_reclaims_container_not_destroyed`
asserts `sandbox.destroy` is never called on session end. A sandbox persists across
many sessions; only the claude session ends.

## How the in-container plugin reaches the bot token

3.1 copies the whole `~/.claude` at `create` (D8), which includes
`~/.claude/channels/telegram[-<profile>]` (token + allowlist). `absd-session` sets
`TELEGRAM_STATE_DIR=/home/dev/.claude/channels/telegram` (default) or
`…/telegram-<profile>` (named) — exactly where the copy lands (host
`~/.claude/channels/telegram*` → container `/home/dev/.claude/channels/telegram*`).
So a same-bot sandbox session's plugin has the token + allowlist and can poll. (New
bot / restricted-credential handling is a later stage — 3.2 scopes to the existing
bot + host-copied creds.)

## Image tag bumped: v1 → v2

The Dockerfile changed (added **bun** — the Telegram plugin's MCP-server runtime,
without which `claude --channels plugin:telegram` cannot poll from inside — plus
`unzip` for bun's installer, and the `absd-session` launcher). So the pinned tag is
now `absd-sandbox:v2`. **Migration:** `abs sandbox build --rebuild`, then re-create
sandboxes to get a v2 container. A v1 sandbox still shells in fine but can't host a
session (no launcher, no bun). Verified in the built v2: `dev` user, `absd-session`
executable, `bun 1.3.14`, `claude`, `node 24`.

## Security recon (the hostile-reviewer walkthrough, container edition)

- **The whole `~/.claude` is copied into a same-bot sandbox** — including the bot
  TOKEN and allowlist and any other credentials/plugins. So a sandbox session for
  untrusted work runs code with the operator's bot token present inside the box. A
  compromise inside the sandbox could read the token from
  `/home/dev/.claude/channels/telegram/.env`. **Recommendation (documented for the
  operator): use a DEDICATED bot / restricted credentials for a sandbox you'll run
  untrusted code in** — the copy diverges from the host, so a per-sandbox token
  never touches the host bot. Restricted-creds tooling is a later stage; for now the
  tradeoff is the same D8 exposure 3.1 already prints at create.
- **Container escape surface**: unchanged from 3.1 — no `--privileged`, no docker
  socket, one bind (the workdir), non-root `dev`. `docker exec` adds no mount. The
  session is as isolated as the box (5.6).
- **The daemon never trusts the container**: liveness is the host-side pane signal;
  the daemon never reads container state for a trust decision.

## Honest gaps / what breaks first

- **No in-container ABS hooks / system prompt / kill ladder.** `absd-session` runs
  plain `claude --channels` — it does NOT reproduce abs.sh's smart-silent, guard, or
  statusline hooks, nor the injected "always reply / report when done" system
  prompt (those live on the host). So a sandbox session is a barer claude with a
  Telegram channel. **`ABS EXIT` from Telegram reaches claude in the box (the plugin
  delivers it) but is NOT hook-enforced** — end a sandbox session by exiting claude
  in the attached session, `abs sessions` + engine kill, or the reclaim when claude
  exits. Full in-container hook parity needs abs.sh + its deps inside the box — a
  later stage.
- **`abs start sandbox` (terminal) writes host `session.pid = $$`** — the docker-exec
  CLIENT pid, a HOST pid — so the always-on daemon yields (via the existing
  `session.pid` check) while the terminal sandbox session is live and reclaims when
  it ends. This is a different mechanism from the daemon-initiated path (pane-only):
  both correct, documented, but two code paths.
- **Attach** works unchanged (`abs attach <profile>` → the engine session whose pane
  is the docker exec → you land in the in-container claude TUI). Detaching leaves the
  container AND the session running (documented in the manual test). Not separately
  automated (real-claude/attach is the human's test).
- **No resource limits** on the container (carried from 3.1).
- **The real-docker session test uses a `sleep` stand-in, not claude** — it proves
  the pane-liveness SHAPE (pane alive → kill in-container proc → pane dead → is_alive
  False → container survives), never running real claude/telegram. The
  claude-actually-responds-over-Telegram path is the human's manual test.

## Deviations from PLAN.md

- Image v1 → v2 (bun + launcher), per the brief's "rebuild the pinned tag, bump".
- The terminal path is `abs start sandbox [name]` (execs docker exec directly,
  writing a host `session.pid` = the exec-client pid for daemon-yield); the daemon
  path uses pane-only liveness. Documented above.
